## Project

FaMiGo is a family chore/reward app: parents assign tasks to children, children mark them done, parents approve them and the child earns stars, which the child can spend on reward options defined by the parents. UI text, comments and exception messages are in German.

Stack: Java 21, Spring Boot 3.5, Vaadin Flow 24.8 (server-side Java UI, no REST API), Spring Data JPA + PostgreSQL 17, Lombok. Installable as a PWA (`@PWA` on `FamigoApplication`).

## Commands

```bash
./mvnw spring-boot:run                       # dev mode (Vaadin dev server, hot reload via devtools)
./mvnw test                                  # @SpringBootTest tests against a Testcontainers Postgres (needs Docker, no local DB)
./mvnw test -Dtest=FamigoApplicationTests    # single test class; add #methodName for one method
./mvnw clean package -Pproduction            # production jar (runs vaadin prepare-frontend/build-frontend)

docker compose up -d                         # start only the Postgres DB (the default, profile-less service)
docker compose --profile full up -d --build  # also run the app in a container, reachable at http://localhost:8081
```

- **Database ports:** the DB is on host port **5433** (a native Postgres already occupies 5432 on the dev machine). Locally the connection details come from `spring-boot-docker-compose`; the app container uses `db:5432` via `SPRING_DATASOURCE_URL`. Credentials live in `.env` (template `.env.example`, not committed).
- `spring-boot-docker-compose` starts the DB automatically on a local app start (`lifecycle-management=start_only`, so the DB stays up when the app stops). It is disabled inside the container.
- The schema is managed by **Flyway** (`src/main/resources/db/migration`, `V1__baseline.sql` = pre-Flyway schema, `baseline-on-migrate`). `ddl-auto=validate`: every entity change needs a new `V<n>__*.sql` migration.
- Testcontainers on Docker 29+ needs `api.version=1.44` (set in the surefire config in `pom.xml`).
- Files under `src/main/frontend/generated/`, `package.json`, `tsconfig.json`, `types.d.ts` are generated by Vaadin. Don't edit them by hand.

## Architecture

Layers in `src/main/java/infokom/info/famigo/`: `entity` → `repository` (Spring Data) → `service` → `views` (Vaadin). Views are Spring beans, get services through constructor injection, and call services. Write use-cases are `@Transactional` service methods (`TaskService.assign/submit/submitFromTemplate/approve/reject`, `RewardService.redeem/fulfill/acknowledge`) that load entities fresh by ID and throw `DomainException` subclasses (`exception/`). Views call them through `UiActions.run(...)`, which shows domain errors as a notification. `User` and `Task` have `@Version`, so never save the session `User` snapshot. Use `UserService.getCurrentUser()` (fresh from the DB) for stars and children.

**Authentication is custom. Spring Security is not used** (only `BCryptPasswordEncoder` from `SecurityConfig`):
- `AuthService` registers users and checks passwords. `SessionService` stores the logged-in `User` entity in the `VaadinSession` under `"loggedUser"`.
- Access control is per view: a view implements `BeforeEnterObserver` and forwards to `LoginView` when `!sessionService.isLoggedIn()`. Nothing enforces roles at the route level, so a new view needs its own check.
- `LoginView` is mounted at `""`. After login, the user is routed by role: `PARENT` → `parent`, `CHILD` → `child`.

**Routing / layout:** every view that requires a login uses `layout = MainViewLayout.class`. `MainViewLayout` builds the header (logo, `NotificationPopup`, logout) and the bottom nav. The nav buttons are role-aware: they toggle between home and a subpage using hard-coded route strings (`tasks`/`child/tasks`, `rewards`/`child/rewards`/`child/stars-exchange`). The middle button opens `TaskDialog` for parents and goes to the star exchange for children. If you add or rename routes, update both the click handlers and `updateButtonText()`.
- Parent routes: `parent`, `tasks`, `rewards`, `manage/rewards`
- Child routes: `child`, `child/tasks`, `child/rewards`, `child/stars-exchange`

**Domain model:**
- `User` has a single table for both roles (`UserRole`). Parent↔child is a self-referencing `@ManyToMany` over the `parent_child` join table (`children` is the owning side and eagerly fetched). A `ParentChild` entity is mapped to the same table.
- `Task` lifecycle (`TaskStatus`): `PENDING` → `DONE` (the child marks it done) → `APPROVED` (a parent approves it and adds `starsReward` to `User.stars`). Tasks can come from `TaskTemplate`s.
- `Reward` links tasks to children for the approval views. `RewardOption` is a redeemable item with a star `cost` and a `RewardCategory`. `ChildRewardTransaction` records a redemption (`implemented` = the parent fulfilled it, `viewedByChild` = the child saw it).
- `DataInitializer` / `RewardDataInitializer` seed task templates and reward options when their tables are empty.

**Live updates:** `@Push` is enabled. `NotificationService` keeps a map from user ID to `UI` plus a refresh `Command`. `MainViewLayout` registers the current UI when it attaches and removes it on detach. `notifyUser(id)` runs that user's refresh through `ui.access(...)`. Only one UI is kept per user, so a second tab replaces the first.

**Styling:** a single theme, `src/main/frontend/themes/my-theme/styles.css` (`@Theme("my-theme")`), with CSS classes prefixed `famigo-`. Components set these classes through `addClassName(...)`, sometimes together with inline `getStyle()` calls.

**HTTPS:** a keystore and certificate (`famigo-keystore.p12`, `famigo.crt`) are in `src/main/resources`. They are git-ignored and not configured in `application.properties`, so the app runs over plain HTTP on 8080.
